# Habitude Constitution

Habitude is a small full-stack habit tracker built as an AI-assisted capstone demo.
This constitution is the highest-authority document in the repository. Every spec,
plan, task list, and code change must comply with it. When another document
conflicts with this one, this one wins.

## Core Principles

### I. Spec-First, Always
No production code is written without a feature spec in `docs/specs/NNN-name/spec.md`
and an accepted plan (`plan.md`) and task list (`tasks.md`) in the same folder.
Specs describe WHAT and WHY in technology-neutral language; plans describe HOW.
A spec with unresolved `[NEEDS CLARIFICATION]` markers cannot move to planning.

### II. Vertical Slices, Independently Shippable
Each user story is a vertical slice (API + UI + tests) that delivers value on its
own. Priority P1 stories form the MVP. A story is "done" only when it is
demonstrable end-to-end, not when its backend or frontend half is merged.

### III. Test-First (NON-NEGOTIABLE)
Tests are written from the spec's acceptance scenarios before implementation.
Every functional requirement (FR-xxx) maps to at least one automated test.
The cycle is Red → Green → Refactor. A pull request with untested behavior is
not mergeable. See `docs/testing.md` for the test pyramid and tooling.

### IV. Simplicity and YAGNI
Build the smallest thing that satisfies the spec. No speculative abstractions,
no configuration for hypothetical futures, no extra dependencies without a
sentence of justification in the plan. Prefer boring, well-documented tools.

### V. Explicit Contracts
The REST API is the single contract between frontend and backend. It is
described by the OpenAPI document generated by the backend and mirrored by
typed clients on the frontend. Breaking changes require a new spec and a
version note in `docs/specs/README.md`.

### VI. Local-First, Privacy-Respecting
The app runs fully on a developer laptop with SQLite and no external services.
User data never leaves the machine unless a spec explicitly introduces sync.
No telemetry, no third-party analytics.

### VII. AI-Assisted, Human-Accountable
AI agents (Copilot, Claude, etc.) draft specs, plans, code, and tests following
`AGENTS.md`. A human reviews and approves every merge. Agents must cite the
spec/FR they are implementing in commit messages and PR descriptions.

## Technology Constraints

- **Backend**: Python 3.13, FastAPI, SQLModel (SQLAlchemy + Pydantic), SQLite,
  Alembic for migrations, `pytest` for tests, `ruff` for lint/format, `mypy --strict`.
- **Frontend**: TypeScript (strict), React 19, Vite, TanStack Query, React Router,
  Vitest + Testing Library for unit/component tests, Playwright for end-to-end.
- **Tooling**: A single Python virtual environment at `.venv/` hosts `specify-cli`
  and backend tooling. Node 22 LTS with `npm` for the frontend.
- **Layout**: `src/backend/` and `src/frontend/`; docs in `docs/`; specs in
  `docs/specs/`; agent instructions in `AGENTS.md` and `.github/`.
- **Accessibility**: All UI meets WCAG 2.1 AA. Keyboard navigation and screen
  reader labels are requirements, not enhancements.
- **Performance**: API endpoints respond in under 200 ms p95 on a laptop with
  10k check-ins; first contentful paint under 1.5 s on a cold local load.

## Development Workflow

1. `/speckit-specify` → spec in `docs/specs/NNN-name/spec.md`
2. `/speckit-clarify` (optional) → resolve ambiguities in-place
3. `/speckit-plan` → `plan.md`, `research.md`, `data-model.md`, `contracts/`
4. `/speckit-tasks` → `tasks.md` with dependency-ordered, testable tasks
5. `/speckit-analyze` (optional) → consistency report across artifacts
6. `/speckit-implement` → execute tasks; tests first, then code
7. Pull request → CI green (lint, type-check, tests) + human review → merge

Quality gates that block merge: failing tests, lint or type errors, coverage
below 85% on changed backend modules, missing spec reference, accessibility
violations flagged by automated checks, or any principle above being violated
without a documented, approved exception in `plan.md` under "Complexity Tracking".

## Governance

- This constitution supersedes all other practices in the repository.
- Amendments require a pull request that updates this file, bumps the version
  below, and lists the rationale and migration notes in the PR description.
- Versioning follows MAJOR.MINOR.PATCH: MAJOR for principle removal or
  redefinition, MINOR for a new principle or section, PATCH for wording fixes.
- Every plan's "Constitution Check" section must reference the version it was
  validated against.
